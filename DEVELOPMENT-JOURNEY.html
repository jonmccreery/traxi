Four development sessions, roughly thirty-six hours, one Android app for a discontinued Qstarz BT-Q1000XT GPS logger — reconstructed 2026-09-07 from the exported transcripts (session1.txt–session4.txt), the git history (48 commits), and ENGINEERING-RECORD.md. The linear sequence, the design decisions, the times it went sideways, and how each was closed.

Part I · session1.txtZero to hardware-verified

Sep 5, 11:00 → Sep 6 ~10:30 · "when i'm on trail, my phone -is- my computer."

1Survey and corrections

The prep doc and the existing Python parser were run against the raw flash dumps, establishing the golden pair used by every test since: cdt_v2.bin (5,376,000 bytes) → 126,613 fixes, 0 checksum failures, 82 sectors, spanning 2025-03-16 → 2026-09-04. Three prep-doc claims died on contact with raw bytes: the "sentinel table" (31 bad records) was a GPX %.1f rounding artifact — there was one; the format register never changed mid-log (the "segments" were power cycles); the spike count was 42, not 26, and 40 of them carried VALID == 2, so masking on VALID became the quality rule. Device format at this point: FMT_REG 0x000A003F, 42-byte records, firmware AXN_1.30-B_1.3_C01, all timestamps needing the +1024-week GPS rollover.

2The Kotlin parser, and the sentinel that wasn't 90.0

:core was built as a pure-JVM module with a golden-file test asserting the exact fix count. Two failures immediately exposed that the sentinel latitude is 89.9999999999996 — raw double bits 40567FFFFFFFFFE4 — not 90.0. An exact-equality mask would have compiled, reviewed cleanly, and silently masked nothing. Fix.isSentinel became a tolerance test. The GNSS technical document also landed here, overturning the "0.1 m elevation quantization" claim (another GPX artifact) and measuring ~2 m 1σ vertical accuracy across 103 stationary stops.

3The protocol layer, and a bug caught before hardware

The round-trip test caught awaitSentence returning on match and discarding every sentence already parsed after it in the same read batch. Over real RFCOMM — where a 64 KB block arrives as 32 sentences of the form $PMTK182,8,<addr>,<4096 hex>*XX — that would have dropped most chunks of every block read. Fixed before hardware ever saw it.

4Bluetooth, four failures deep

The app parsed the real 5.4 MB image on the phone to an exact golden match — then Bluetooth failed four different ways, each presenting as nearly the same opaque socket error:

  • Crash on pair — CompanionDeviceManager.associate() throws IllegalStateException synchronously, bypassing its failure callback, when the manifest lacks <uses-feature android.software.companion_device_setup>.
  • Association ≠ bonding — CDM association creates no link key; RFCOMM needs one. Bonding.ensureBonded() added.
  • A filter that dropped devices — setNamePattern(".*") only tests devices whose names have resolved; replaced with an empty filter plus a "Likely loggers" UI split.
  • The PIN — 1111 was rejected with a bare AuthenticationFailed; 0000 paired immediately. The device uses legacy BT 2.0 PIN pairing, not SSP; Bonding.KNOWN_PIN = "0000" went into code and UI copy.

A USB detour identified the hardware — 0e8d:3329, native CDC-ACM, no bridge chip — and decoded two "device lies" as host-side failures: $PMTK182,2,9 returns a JEDEC RDID (1C 70 17 = EON, capacity 0x17 → 8 MB), and status field 8 is a write-pointer byte address (0x0051F3C2 = 5,370,818), not a record count. The laptop reference dump was set here: 5,505,024 bytes in 83.5 s, zero retries, zero corruption.

5First BT download: three transfer bugs at once

The first real download died after one block, exposing: a fixed 10 s block timeout (only 20,480 of 65,536 bytes had arrived — replaced by an idle timeout that progress resets, 240 s hard cap); no stream reset between requests (stale chunks from the abandoned block poisoned the next — resetStream() added); and filled == 0 treated as end-of-flash (wrong — erased sectors still answer, with 0xFF, which is byte-identical to a missing chunk; termination became "two consecutive unwritten blocks"). Regression tests use an injectable clock and assert >30 s of simulated time so they cannot degenerate.

6The stale link key

Sideways

After a device power cycle, connects failed with no PIN prompt. The user: "the one time we successfully connected from this device, i was prompted for a pin. this isn't happening now. why?" dumpsys showed bredr_linkkey_known:T … bredr_authenticated:F bredr_encrypted:F — the legacy device forgets its link key across a power cycle while Android keeps hers as BOND_TYPE_PERSISTENT, so BOND_BONDED lies and ensureBonded() short-circuits.

On connect failure while "bonded": removeBond() via reflection, delay, re-pair, retry. The PIN prompt returned and the download restarted.

7493 B/s, a wrong fix, and a rule that held forever

The download ran at ~493 B/s. A reader-thread rewrite (theory: polling available() throttled it) measured identical — because the real cause is arithmetic: 493 B/s of decoded payload is ~986 hex chars/s on the wire, i.e. a 9600-baud UART — the internal bridge between the logger's Bluetooth module and GPS chip. A full read is ~3 hours and no host software can change it.

Sideways

The user caught the rewrite regressing: "we've regressed. check the log. it failed this time instead of slowed." It had introduced a new failure mode and its failure path returned zero bytes where the previous run had kept a 64 KB partial.

Reverted (c13ebf5), establishing the project-long rule: never discard a partial download. FlashDownloader records the failure and returns the bytes read; partials are saved unconditionally; Result.isComplete distinguishes outcomes.

8Incremental download

planIncremental made the slow link irrelevant: a wrap probe reads records at PROBE_OFFSET = 512 — the oldest data, first overwritten in OVERLAP mode — and compares against the previous dump (records, not sector headers, which look alike across a wrap), falling back to a full read on mismatch. The final block is always re-read because its sector header was mid-write (count 0xFFFF). First hardware run found the probe requesting 512 bytes, which the real device ignores and answers by dropping the RFCOMM link — it had been sized against the permissive simulator. Second run: 10 m 32 s, 4 blocks instead of 82, byte-identical through the write pointer, 126,644 fixes (+31 real ones).

9The erase reversal

The user revealed the bedrock use case: "the -critical- feature on a thru hike… the bedrock goal was dump, erase, repeat until the end of the trail." Erase went from deliberately-out-of-scope to the app's reason to exist; the assistant named its own error — "my safety argument was correct, but I used it to justify not building the feature instead of building it carefully" — and §0.2 was written with a seven-clause gate: verified same-session dump; coverage past a freshly read write pointer; typed confirmation naming the exact fix count; never reachable from a download callback; disable → erase → re-enable with a long timeout; read back sector 0 to confirm 0xFF; never delete the pre-erase dump.

10The USB corruption saga

USB in the app was hand-rolled CDC-ACM (~150 lines, chosen over a JitPack dependency). First contact: writes accepted, zero bytes back — this device's CDC interfaces are reversed (if0 = DATA with the bulk endpoints, if1 = COMM), so the hardcoded wIndex = 0 sent SET_CONTROL_LINE_STATE to the wrong interface and DTR was never asserted. The device is mute until it is. Fix: wIndex = 1.

Then the corruption: roughly 1 block in 8 short on the phone, zero on the laptop over the same cable. Instrumentation the user pushed for exposed the worse half: readLogBlock pre-filled its buffer with 0xFF, so lost chunks left holes byte-identical to erased flash (proven by a diff at 0x002C17FC). Damage detection (Result.damagedRanges, "DOWNLOAD DAMAGED") made the loss loud before anything tried to fix it. Then five fixes failed or made it worse:

AttemptResult
Floor the bulk read timeout at 250 msNo change
Hand-rolled reader thread keeping a read postedWhole-chunk gaps 5 → 0; corruption remained
Raise the transfer timeout to 10 sWorse
Split requests into 8 KB for flow controlWorse; reverted
Swap to usb-serial-for-android 3.8.1Gaps 5 → 1; same corruption character

The one clean win was the retry idle timeout: chunks arrive ~33 ms apart, so a 10 s wait before retrying was 300× any legitimate gap — 58% of a 240 s run was retry idle. At 2.5 s: 152 s, 0 unrecovered damage, 129,115 records, first diff exactly at the old write pointer. The corruption was survived, not fixed — and the session closed with a 462-line handoff preserving the clue: malformed sentences quantized at exactly 2,840 chars (9×) and 6,961 (2×), against a healthy 4,119 ($PMTK182,8,AAAAAAAA, = 20 + 4,096 hex + *XX). Nine lines on the same byte count is a fixed buffer boundary, not packet loss; 6961 = 4119 + 2842 is one good sentence with a fragment welded on; and the loss was one off from 1280 = 20 × 64 — a whole number of max-size USB packets.

Sideways

Abort drive. The hand-rolled transport was defended through hours of failed fixes. The user: "you've been defending your hand rolled communications protocol that you argued for because of a single dependency… you're running into abort drive… let's just fix it."

The library swap — which didn't fix the corruption either. Survival across a rewrite and a swap became the diagnostic signal Part II ran on: the defect lived in the primitive, not the code around it.

Sideways

Blind taps and a battery scare. Coordinate taps connected to the user's Denon amp (C4:30:18:C9:61:76), wandered into Android's USB settings, and nearly touched a share sheet listing contacts. A no-charge-LED scare produced a physically impossible wattmeter reading, and a proposal to drain the cell for a conclusive test — vetoed: "i'm not going to waste potentially the last power this thing ever gets on a test. that would be crazy." Fixed by reseating the battery.

Automation halted each time; "screenshot or dump UI state before tapping" became a standing rule. The meta-lesson went into the handoff: separate signal from interpretation — "Signal keeps. Frames rot."

Sep 6, morning → ~17:15 · "let's get back into the transport bug… this one's got my interest piqued :)"

1The mic-drop fix

Instead of testing hypotheses on hardware, the session decompiled the dependency — unzip the cached AAR, javap -p -c CommonUsbSerialPort.class — and read the mechanism in thirty lines of bytecode:

if (timeout != 0) nread = mConnection.bulkTransfer(ep, dest, len, timeout);
else { mUsbRequest.queue(ByteBuffer.wrap(dest, 0, len), len);
       mConnection.requestWait(); nread = buf.position(); }

bulkTransfer returns −1 on timeout and discards the bytes already received into that URB — the caller can't even learn how many there were. The app passed readTimeout = 200, so every read took the lossy path. Fix: readTimeout = 0, selecting the UsbRequest path, which has no timeout to expire and nothing to discard; plus readBufferSize 64 → 4096. First run: 0 retries, 0 malformed lines, 0 gaps, slowest block 1,317 ms (was 10,782), ~110 s wall, byte-identical across the 5,479,850-byte common prefix. "decompiling the library to find it with immediate problem resolution as a result is a mic drop."

Two footnotes with teeth: readTimeout = 0 would have worked in the hand-rolled version too, but an infinite bulkTransfer parks a thread in an uninterruptible native ioctl — UsbRequest is cancellable via port.close(). The library did not supply the fix; it supplied a read path the fix could be applied to. And the new delivery histogram showed the firmware emits ~512-byte units split 1 + 511, every delivery ≤ 537 bytes — so the earlier "no short packet terminates the read" theory was struck through as wrong.

2The post-mortem (§4.1)

Why did the bug survive a rewrite and a library swap? bulkTransfer is the discard-on-timeout API, and it was the only read primitive any version used. The original was worst: awaitSentence handed a shrinking deadline down as the URB timeout — 500 ms, 200, 50, 5, floored at 1 ms — a positive feedback loop (lose bytes → block runs long → shorter timeouts → more discards) that explains the bimodal block times and ~1-in-8 clustering. The reader thread enlarged the loss quantum to 16 KB; the library swap shrank it to 64 bytes. Every attempt moved the quantum of the discard; none removed the discard. The old instrumentation had the answer all along: reads=46250 timeouts=90 (0.2%) — 90 timeouts were 90 discard events, read as noise. The lesson, verbatim: "When one symptom survives several well-reasoned fixes, stop tuning parameters and go read the primitive."

3Erase, built carefully

Pmtk.WRITE_ERASE_FLASH = "PMTK182,6,1" reversed the "deliberately absent" decision. A pure EraseGate implements all seven §0.2 clauses; FlashEraser runs disable → erase → verify → restore; the erase ack has a 90 s budget and no retries (a timeout probably means the erase is still running, and a re-send could interrupt it); verification reads back a full block where a short read counts as failure (missing bytes read as 0xFF — the exact value being verified); the typed confirmation is the exact fix count (129186), deliberately not rememberSaveable. Erase evidence exists only when a download completed and that exact file parsed cleanly, invalidated by any new download or disconnect. Hardcoded capacity text the user caught ("it'll always be incorrect") became continuousLoggingDays() derived from live flash ID, interval, and record size. A self-introduced bug — the erase card's LaunchedEffect injecting a status query mid-block-read — was caught in transcript review and fixed with a busy guard.

4The silent capture failure (§12)

The user noticed the GPS light not blinking: "did we disable logging along the way?" The latent bug surfaced first — every config write is a three-step sequence, because the device refuses config changes while recording:

c.writeLoggingEnabled(false)          // 1. stop
c.writeConfig(TIME_INTERVAL, "50")    // 2. change the setting
c.writeLoggingEnabled(true)           // 3. start

— with no finally. If step 2 threw, step 3 never ran; the deliberate disable survived power cycles as saved configuration, and the user was told only that a setting change had failed.

Sideways

"The app didn't do it." Claimed on an in-memory transcript the assistant's own two APK installs had destroyed. The user: "it's unexpected state change that could lead to real world, irevocable, silent failure of data capture… i want to be -extremely- careful in the analysis of why this happened."

Withdrawn ("That was wrong of me and I withdraw it"), and the forensics moved to the flash — which the process cannot destroy. The device writes a type-0x07 marker on every logging start/stop; MtkLogParser.StatusChange recovers them. Finding: one new marker, DISABLE after 2026-09-06T16:16:10Z at 0x0053CBCA, unanswered. Across 417 status changes in 18 months, the double-DISABLE fingerprint appears 0 times in 17 months, 3 times starting 2026-09-05 — the day the app began writing config. ~1h40m of real time unrecorded, through a power cycle and a re-pair, looking completely normal.

A wrong invariant was caught by the golden file itself: "a healthy history never ends disabled" fails on cdt_v2.bin (power-off writes a trailing DISABLE, answered at next power-on); narrowed to "no unanswered stop." Mitigations: withLoggingPaused restores logging in a finally — one place, in the tested module, with an onRestoreFailed callback (it must reach the caller when the body also threw); a decoded LogStatus (bit 0x0002 = logging, cross-checked against GPSBabel's log_status & 2) with NOT RECORDING in error colour and a Resume control; a USB-detach watcher; RecordingAudit reporting unanswered stops from any dump, forever; and the alarm-hygiene rule — silence is the good news, explanation() returns null on healthy dumps, encoded in core. v1 closed: main fast-forwarded, tag v1, the handoff renamed to ENGINEERING-RECORD.md with §12 written.

5The bug "resurfaces" — and the device exonerates the app

A parallel session (the Traxi rename, telemetry, launchExclusive serialisation) reported the disable bug twice more. Reopening the root cause found a genuinely gnarly hole in the v1 fix: finally runs on cancellation, but suspending calls inside it throw CancellationException before sending a byte. The restore called withContext(Dispatchers.IO) — on a cancelled coroutine that throws immediately: disable out, enable never sent (PROBE sent: [PMTK182,5]). The v1 fix had closed the exception path and left the cancellation path open; the simulator masked it because its write never suspends. ("whoooooaaa!!! that is a -gnarly- failure mode.") Fixed with withContext(NonCancellable) and a regression test using a transport wrapper that actually suspends, verified to fail on the old code (cb193c7).

The controlled experiment cut deeper: $PMTK182,4 from raw Python over /dev/ttyACM0, no app attached — the device acks PMTK001,182,4,3 (success), writes ENABLE and DISABLE markers itself, and the pointer stays frozen. The device accepts the command, acknowledges it as successful, and turns itself back off. The v1 attribution was retracted: "I picked the explanation that matched the bug I'd just found… exactly the reasoning error I warned about in §4.1, and I made it anyway."

6Recovery, act one

Research found the leaked MTK GPS Logger Library User Manual 1.2 (Andy Lee, 2006, "MTK CONFIDENTIAL," via rigacci.org), documenting NEED_FORMAT_BIT and the engineering commands 9–12.

Sideways

The ENABLE_LOG misstep. Undocumented $PMTK182,10 sent on the prediction "worst case rejected or a no-op." Wrong on both: no acknowledgement at all, status 0x0100 → 0x0504, write pointer moved to 0x00000002 — on hardware that cannot be replaced, in a command family that includes WRITE_LOG <addr> <data>.

Sector 0 verified byte-identical (nothing lost). Decoded via BT747's bitmask table (0x0400 = need_format, 0x0100 = enabled, 0x0004 = stop-when-full), the misstep had revealed the true state — the log area was genuinely unformatted. "I mispredicted the command, and it happened to produce the diagnosis anyway. That's luck, not judgement." Commands 9–12 documented as engineering tooling, never to be used.

$PMTK182,6,1 (FORMAT LOG ALL) ran — SPI busy ~22 s, need_format cleared, 18 months of multiply-copied track erased. Logging still refused to hold. A format also silently resets configuration (RCD METHOD → STP, BY_SEC → 1.0 s, FMT_REG → 0x0002002F); OVP was restored via $PMTK182,1,6,1 — still refusing. Tension peaked ("what!@!!!!!!!! did you just tell me that my logger, that used to log, is great for everything except logging now!!!!!!") until the untested step: a power cycle after the format — the firmware keeps pre-format state in RAM and must boot onto the clean log area. "oh. my. fucking. god… that worked!!!!!" Two more truths: the LED means GPS fix, not recording (steady blink, 3D DGPS fix, zero bytes written — "that LED has misled both of us all day"), and the user's priority correction into persistent memory: the device outranks the data.

7Between sessions: the solo recovery

Off-session

After session II the device stopped holding its enable again. The fingerprint: an enable that takes and then reverts — START_LOG acked, the auto_log bit 0x0002 clearing itself within the second, "ENABLE->DIABLE every time for hours" — and an ordinary power cycle did not clear it. The user, alone: an SPI-level flash format from the EON datasheet (the exact spi_-prefixed command was never captured — flagged in §13 as "the single most valuable missing line"), then "a full despair and mourning period," then a just-in-case retry after a power cycle — which held.

The flash journal corroborates it verbatim: paired LOGSTAT 258/256 markers at offsets 0x0300–0x04B0, the device's own record of each round, ending in the one enable that stuck. Between the format and the next boot a recovered device is indistinguishable from a dead one: "Do not declare death between steps 1 and 2."

3The Bluetooth regression, root-caused in git

"download over bluetooth fails now." The link was healthy — every config query succeeded — but the 64 KB block read came back short: 18,432 bytes, then 2,048, then nothing. The arithmetic convicts the timeout: a 2048-byte payload chunk is a 4,121-byte sentence on the wire; at 493 B/s that is ~8.4 s per chunk, against FlashDownloader.BLOCK_IDLE_TIMEOUT = 2_500 — the USB-tuned constant from 023e9b3. Bluetooth had been verified against the earlier 10 s default; the later commit was "correct for USB and quietly fatal for Bluetooth."

The fix (d346a7e): the idle timeout became a property of the transport — Transport.blockReadIdleTimeoutMillis, default 10 s (slow-link-safe: "fast transports opt down"), UsbSerialTransport overriding to 2.5 s, the constant deleted. Guarded by a regression test (a GappyTransport inserting a 4 s gap every 5th read, with a stepped clock) falsified by reintroducing the bug — and held uncommitted until hardware proved it: a full 3-block BT download, block 0x00000000 65536/65536 bytes, 32 chunks, 161979 ms (~2.7 min/block), clean stop on two unwritten blocks, 306 fixes. Mid-flow the assistant noticed the phone was in an active call and backed off entirely ("No taps landed; I backed off as soon as I saw it").

4Flow, not just totals

"i'd like to know that things are flowing rather than received." Built bottom-up (ba09b54): an onChunk callback in readLogBlock; Progress.blockBytes/blockSizeBytes; a per-sector bar with KB and rate — no percent-of-flash, because the device's totals are untrustworthy, but the 64 KB block is "a denominator we can stand behind" — and a Live-tab heartbeat (pulse, "last update Xs ago", rate).

Sideways

584 sentences per second. The first rate used an EMA of inter-arrival gaps; RFCOMM delivers a second's worth of sentences in one burst, so sub-millisecond intra-burst gaps inflated the rate ~80× (real: ~7/s). Also a "-0.0 s ago" flicker when a sentence lands just after the UI samples its clock.

A sliding wall-clock window for the rate; a clamp for the age. Verified on hardware: "Sector 1 · 18/64 KB · Speed 3.9 KB/s", bar climbing live.

Then two cleanups (c449fad, 6b6a524): the Live tab counts fixes, not sentences — only a GGA with a position and fix quality > 0, so a receiver alive-but-fixless correctly reads stale — and cancel became immediate: first polled per-chunk (breaking three tests whose limiters counted polls as blocks; fixed to count block boundaries), then — after hardware showed an ~8 s residual, because the BT transport blocks its whole idle timeout during gaps — pushed into awaitSentence with READ_SLICE_MILLIS = 400 read slicing. The partial block is discarded; resume re-reads it cleanly. Final verification was blocked by a wedged SPP slot from repeated reinstall/reconnect cycles, and the session stopped rather than keep hammering the irreplaceable device — an honest gap declared, cancel confirmed effectively instant after the user's power cycle.

5Ground truth over the status bit

A reproducible bug: after any Bluetooth disconnect/reconnect the app showed NOT RECORDING; the Config pane "restored" it. Traced read-only first: neither connect nor disconnect writes to the device, so an explicit disconnect provably cannot stop the recorder — the indicator was a connect-time snapshot (DeviceInfo.logStatus set once in openWith, refreshed only by refreshConfig(), which is why config actions "fixed" it). The device's status bit simply misreports after reconnect.

The user named the real requirement: "what i need most is a way to know if tracks are being logged… my only way is to dump a log and see id the counters increased." The fix inverted the epistemology (95be843): the telemetry loop polls the write pointer (PMTK182,2,8) every 12 s; the Device tab shows "checking…" → RECORDING with a live "N B written to flash since connecting" counter → NOT RECORDING only after 30 s of a frozen pointer. Hardware-verified (96 → 192 → 240 B climbing). The flaky bit was demoted to a secondary "Reported" row. Caveat recorded: distance/speed-triggered modes would legitimately read NOT RECORDING when stationary. "This is the live write pointer, not a guess."

Part IV · session3.txtThe wrap probe, the backfire, the spiral, the last recovery

Sep 6, ~21:45 → 23:15 · "i'm comfortable calling this mtk device project stable…" — and then not.

1The v2 roadmap, recalled and deferred

From §13 of the record: the trail loop as one button (dump → verify → export → erase → confirm), the burn-rate forecast ("dump by <date>", built on the trustworthy write pointer, not the ~2× inflated record count), the recording watchdog, and a download that checkpoints blocks so a 3-hour BT read survives a link drop. Constraints: the watchdog goes first (it attacks the §12 failure class), and the trail loop must not ship before erase runs on real hardware. None were built — "whoops… i just found a bug we need to address first."

2Fetch-new's frozen bar

The wrap probe in planIncremental (FlashDownloader.kt:147) still called readLogBlock(0, blockSize) bare — no onChunk, no shouldContinue, no link-sized idle timeout. Over Bluetooth the probe is the first ~2 minutes of every fetch-new, so the flow opened with a frozen bar and a cancel that silently waited the whole block out. Fixed with full parity (e8790d0); during the probe bytesDownloaded holds constant and only the per-sector bar moves — nothing new is being fetched ("same honesty rule"). Cancel messages were rewritten too — "Cancelled — nothing had been fetched; <source> is untouched" instead of "the logger did not respond" — because "blaming the logger for a stop the user asked for is a lie." Also noted, unresolved: git remote -v returns nothing. One copy of the code, on the laptop that stays home.

3Growth misread as wrap — and the bug that didn't fire

Sideways

"umm… i hit a retry… and the download failed." The chain: fetch-new ran from a dump whose last real byte was 0x73BF (sector 0 count still 0xFFFF, mid-write); the probe found a difference at 0x73C0 and declared "the log has wrapped or been erased," forcing a full download — during which the BT link genuinely decayed and died (26,624 → 2,048 → 0 bytes), after which the write-pointer poller hammered the dead-but-open socket every 3 s: 99 failed retries and counting, no ACL broadcast because Android still considered it connected.

The deeper find was the bug that didn't fire: had the probe matched, the old last-block extend rule would have copied the stale mid-write block forward, silently dropped every record since 21:39, and reported "Added 64 KB of new tracking" — eligible as erase evidence. "Tonight the wrong wrap verdict accidentally protected you by forcing the full path."

Three fixes in f0e105d: a three-case byte comparison (a byte that was 0xFF in the previous dump proves growth; only real bytes convict — changed to data = wrapped, changed to 0xFF = erased); extend from the write frontier (re-read from the block containing the last real byte); and a byte-exact test reconstruction of that night's dump shape. Plus a dead-link detector — the part that backfired.

4The backfire

Sideways

"that last update kills bluetooth connection… but sometimes… looks like a race condition…" The phone transcript separated two drops: one a genuine ACL radio disconnect; the other the new detector (DEAD_LINK_SILENT_PROBES = 2, ~30 s of silence), killing a link that had merely gone quiet after connect-time queries this device answers unreliably timed out. Before the detector that stall was invisible and self-healing; after it, a recoverable stall became a hard disconnect on a fragile reconnect path. "I made a flaky-but-recoverable link into a flapping one."

Reverted (10ff393) with one condition that fixes both the zombie poller and the teardown: probe only a link that is talking (bytesSincePump > 0), wait a full interval before the first probe, never tear down on silence, trust ACTION_ACL_DISCONNECTED as the real signal. The lesson entered persistent memory: surface, don't auto-remediate. Alongside: 51 lines of standing explainer text removed ("alarms, not disclaimers" — RECORDING WAS LOST and checksum warnings stayed), and the download notification made to leave with the download — cancel the collector scope before stopForeground so a post-mortem notify() can't re-post an orphan (54db183, aad2fc9).

Sideways

The design decisions that held

Transfer integrity

Never discard a partial download. Established after a rewrite revealed failures were throwing bytes away; enforced since — partials saved unconditionally, damage enumerated as byte ranges (Result.damagedRanges), never silent, never called a verified copy.

Architecture

The idle timeout belongs to the transport. Slow-safe default (10 s), fast transports opt down (USB: 2.5 s). The regression it fixed came from tuning a shared constant for one link.

Epistemology

Ground truth over device claims. The record count is ~2× inflated, the status bit misreports after reconnect, the LED means fix — but the write pointer is bytes actually in flash. Recording status, capacity math, and erase evidence all build on measured quantities.

Alarm hygiene

Silence is the good news. Alarms only for real loss; explanation() returns null on healthy dumps; standing explainer text trimmed. "Explaining on every ordinary dump why a benign condition is benign is the noise that teaches people to skim."

Operations

Surface, don't auto-remediate. The dead-link detector proved that auto-fixing ambiguous state destroys recoverable state. Probe only a talking link; trust the ACL broadcast; let the human decide.

Safety

All mutations through withLoggingPaused — restore in a withContext(NonCancellable) finally, in the tested module, with onRestoreFailed as a callback. "If you find yourself writing writeLoggingEnabled(false) at a call site, that is the bug being reintroduced."

Method

Read the primitive. The two hardest bugs — the bulkTransfer discard, the cancellation hole — were closed by reading what the code sits on, not by tuning parameters above it. Four parameter changes moved numbers on the near side of bulkTransfer; the answer was thirty lines of bytecode on the far side.

Testing

The simulator must be as strict as the device. Every download bug lived in the gap where it wasn't: the 512-byte probe (link-dropping on hardware), the 10 s timeout, the non-suspending write, the hardcoded status 256.

Record-keeping

Corrections are marked inline, never edited away. §13 corrected twice by the person who lived it; the misread timeouts=90 instrumentation and the ENABLE_LOG misjudgement recorded under their own names. "Several of them are the most useful paragraphs in the document."
